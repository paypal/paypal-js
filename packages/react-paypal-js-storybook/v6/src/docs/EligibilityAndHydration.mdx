# Eligibility and Hydration

Which payment methods to show depends on the **merchant**, the **buyer**
(country, device, browser), and often the **amount**. So you check eligibility
first and render only the methods that are eligible.

There are **two ways** to get eligibility, and one important rule about combining
them.

---

## Path A — client-side: `useEligibleMethods`

Call the hook inside `PayPalProvider`. It fetches eligibility in the browser and
gives you an `isEligible(...)` check:

```tsx
const { eligiblePaymentMethods, isLoading, error } = useEligibleMethods({
  payload: {
    amount: "42.00",
    currencyCode: "USD",
    paymentFlow: "ONE_TIME_PAYMENT",
  },
});

if (eligiblePaymentMethods?.isEligible("venmo")) {
  return <VenmoOneTimePaymentButton {...props} />;
}
```

The `payload` matters for **amount-sensitive** methods — e.g. Pay Later only
qualifies within certain amount thresholds, so passing the amount gives an accurate
answer.

## Path B — server-side prefetch + hydration

On a server-rendered app (e.g. Next.js), fetch eligibility on the server and hand
the result to the provider so the **browser makes no eligibility request at all**:

```tsx
// server component / loader
import { fetchEligibleMethods } from "@paypal/react-paypal-js/sdk-v6/server";

const response = await fetchEligibleMethods({ environment, headers, payload });
```

```tsx
// pass it down to the provider — this "hydrates" the SDK
<PayPalProvider clientId={clientId} eligibleMethodsResponse={response}>
  <PaymentButtons />
</PayPalProvider>
```

Inside `PaymentButtons`, read the hydrated data with the same hook — call
`useEligibleMethods()` with **no payload** and it returns the hydrated result
without triggering a new fetch:

```tsx
const { eligiblePaymentMethods } = useEligibleMethods();
```

This removes a client round-trip and avoids a flash of "loading" before the buttons
appear.

---

## `merchant_origin`: send a bare hostname, not a full origin

When you build the server-side `fetchEligibleMethods` payload, set
`merchant_info.merchant_origin` to your checkout page's **bare hostname** — no
scheme, no port, no path:

```json
{ "merchant_info": { "merchant_origin": "checkout.example.com" } }
```

Despite the `origin` in the field name, this is **not** a full web origin (which
would include the `https://` scheme and any port). It is only the **hostname**
(fully-qualified domain name):

- ✅ `checkout.example.com`
- ❌ `https://checkout.example.com` (has a scheme)
- ❌ `checkout.example.com:8443` (has a port)
- ❌ `https://checkout.example.com/pay` (scheme and path)

Why it matters: domain-bound wallets like **Google Pay** and **Apple Pay** validate
this value against the merchant's **registered domain**, which is a bare FQDN.
Sending a scheme or port makes the wallet reject it — for example, Google Pay
returns an `OR_BIBED` origin error. You only set `merchant_origin` yourself on the
**server** (Path B) payload; the client-side `useEligibleMethods` hook derives it
for you.

---

## The rule: don't mix a payload with hydration

> If you pass `eligibleMethodsResponse` to hydrate **and** also call
> `useEligibleMethods({ payload })` in a child, you get a **redundant** client-side
> fetch.

Why: the hydrated response is stored **without** a payload. A later
`useEligibleMethods({ payload })` call looks for data matching _that payload_,
can't find it, and fetches again on the client — defeating the point of
prefetching. Pick one:

- **Hydrating (Path B)?** Call `useEligibleMethods()` with no payload — it returns
  the hydrated data without fetching. Bake any amount into the server
  `fetchEligibleMethods` payload, not into a client hook.
- **Not hydrating (Path A)?** Call `useEligibleMethods({ payload })` and let it
  fetch on the client.

server `fetchEligibleMethods` payload for Path B, or the
`useEligibleMethods({ payload })` argument for Path A.
